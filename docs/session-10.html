Deuxième passage sur MVC : un contrôleur mince 15 min

Dans CategoryController, chaque action tient en deux lignes : lire ou enregistrer, puis répondre. Avant lui, la Form Request StoreCategoryRequest valide les données ; si elles sont invalides, Laravel redirige vers le formulaire avec les erreurs et old(), et store() n'est jamais appelée.

Après lui, ou à sa place, le gestionnaire d'exceptions de Laravel transforme abort(404) ou abort(503) en réponse : il affiche la vue resources/views/errors/404.blade.php ou 503.blade.php. Idée reçue à écarter : « un contrôleur robuste attrape toutes les erreurs avec try/catch ». Aucune action de Mini-CMS n'en a besoin.

D'où vient un message d'erreur ?

Quiz éclair

Une requête POST arrive sur store(StoreCategoryRequest $request) avec un nom vide. Que se passe-t-il ?

La Form Request est résolue avant l'appel de l'action ; si la validation échoue, Laravel redirige avec les erreurs et old(). Le corps de store() ne s'exécute qu'avec des données valides.

messages() de StoreCategoryRequest définit slug.unique, et lang/fr/validation.php définit unique. Quel message s'affiche pour un slug déjà pris ?

Un message défini pour une règle d'un champ précis dans la Form Request passe avant le fichier de langue (Figure 10.2).

lang/fr/validation.php ne contient pas la clé email. Avec APP_LOCALE=fr, une règle email échoue. Que voit l'utilisateur ?

Laravel cherche la clé dans la locale fr, puis dans la locale de secours (en), dont le framework fournit les messages. Notre fichier ne contient que les règles du projet.

À retenir

Pourquoi ? Chaque responsabilité a sa place : la Form Request valide, le fichier de langue formule les messages, le layout affiche le message de succès, le gestionnaire d'exceptions choisit la page d'erreur. Le contrôleur ne fait plus que relier ces pièces, ce qui le rend court, lisible et facile à tester.

Erreurs fréquentes : Croire qu'un message manquant dans lang/fr/validation.php provoque une erreur : Laravel passe simplement à la source suivante et affiche le texte anglais. Un message resté en anglais signale donc une clé absente ou un fichier mal placé, pas une panne.

app/Http/Controllers/CategoryController.php (contenu complet, à la place de tout le fichier généré) :

<?php

namespace App\Http\Controllers;

use App\Http\Requests\StoreCategoryRequest;
use App\Http\Requests\UpdateCategoryRequest;
use App\Models\Category;
use Illuminate\Http\RedirectResponse;
use Illuminate\View\View;

class CategoryController extends Controller
{
    public function index(): View
    {
        $categories = Category::withCount('posts')->orderBy('name')->get();

        return view('admin.categories.index', compact('categories'));
    }

    public function create(): View
    {
        return view('admin.categories.create');
    }

    public function store(StoreCategoryRequest $request): RedirectResponse
    {
        Category::create($request->validated());

        return redirect()->route('admin.categories.index')->with('success', 'Catégorie créée.');
    }

    public function edit(Category $category): View
    {
        return view('admin.categories.edit', compact('category'));
    }

    public function update(UpdateCategoryRequest $request, Category $category): RedirectResponse
    {
        $category->update($request->validated());

        return redirect()->route('admin.categories.index')->with('success', 'Catégorie mise à jour.');
    }

    public function destroy(Category $category): RedirectResponse
    {
        $category->delete();

        return redirect()->route('admin.categories.index')->with('success', 'Catégorie supprimée.');
    }
}

Par rapport au fichier généré, la méthode show() et l'import inutilisé Illuminate\Http\Request disparaissent. Les types de retour View et RedirectResponse sont ceux de PostController.
